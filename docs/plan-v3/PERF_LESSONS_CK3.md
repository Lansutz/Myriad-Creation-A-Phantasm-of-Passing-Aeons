# 从 CK3「唯主是依」性能日志里能拿的东西

> 来源：Paradox 开发日志 #5（2026-11-09 收到，B站转载）：<https://www.bilibili.com/opus/1245671087174320145>
> 性质：**性能工程**，不是信仰设计。但对我们的 D19（性能门禁）与 S18（信仰）有直接约束。

---

## 1. 他们怎么量的（可直接照抄）

- **指标**：从 1066 年起模拟 100 年，取**每日平均 tick 耗时**；另测启动时间。
- **机器**：2012 年八核 CPU + 16GB，作为"低配参考机"。
- **结论**：游戏后期过一天 < 1 秒；1070→1160 年平均日耗时涨约 **1.5 倍**（系统越跑越多）。
- **一天的时间去哪了**：AI 决策 ≈1/4；并行预更新 ≈1/4；顺序更新 ≈1/5；触发事件 ≈1/10。

⇒ 我们的 M0.5 验收台应直接采用：**100 年 × 每日平均耗时 + 启动耗时 + 分段占比**，而不是"跑一遍不崩"。

## 2. 六个可以直接搬的工程结论

| # | 他们的发现 | 对我们的动作 |
|---|---|---|
| 1 | **预更新 / 更新两段式**：先并行算出"即将发生的变更"，再顺序应用 | 我们的系统是**就地改写**（`PoliticsSimulationSystem` 直接改 stability/tax）。两段式能同时带来并行与确定性；建议在 Scheduler 层引入 `Compute` → `Apply` 两相 |
| 2 | **热路径失控**：某函数从每月 1500 次变 85 万次，只因脚本改动把它挪进了高频调用点 | 需要**每函数调用计数 + 总耗时**的插桩（现在只有系统级耗时）。这比系统级更能定位"一行代码的灾难" |
| 3 | **"先建列表再查里面有没有"** 的成本是直接问的 10 倍 | 我们有多处同型：`RelationRegistry.GetBySource` 全表扫描、`WorldQueryAdapter` 遍历全图、`ContentResolvers` 线性查 | 
| 4 | **空对象检查的间接寻址** 去掉后省 3%（最大单项） | 我们的等价物：`world.realms.ContainsKey(id)` 反复查、`ContentResolver` 每次 `TryGetValue` 再判空。可缓存句柄 |
| 5 | **崩溃修复可能悄悄吃掉 4%**（把清理移到单线程） | 我们的 `SaveSystem` 原子写、`TitleInstanceRegistry.Clear()` 都是"为正确性牺牲性能"的地方，改完要量 |
| 6 | **长列表逐条删除**（每次前移一位）→ 单遍批量删 | 我们 `pendingLaws.RemoveAt`、`DirtySet` 逐项移除、`_byTarget` 字典清理都可批量 |

## 3. 启动时间（我们也有这个问题）

他们的三大启动开销：本地化文件**单线程逐文件**读、**校验码算两遍**、大目录**反复扫描** + **九种语言全枚举**。

⇒ 我们要查三件事：① `ContentRegistry` 是否对每个包域重复扫目录；② 本地化是否全语言加载（只留当前语言）；③ 存档校验/内容校验是否在主菜单前同步跑（应挪到进游戏后）。

## 4. 内存

- 十年后系统内存降 1/6；**内存第 5 年起趋于平稳**（内容在启动时载入，不在游戏里累积）。
- 动画元数据 1200MB → 12MB（同一份数据被每个骨骼各读一遍）。

⇒ 我们要查"是否随年份累积"：`plans`（不入档但会创建）、`chronicle` 条目、`_byTarget` 关系、`DirtySet`、事件历史。**长跑内存曲线应在 M0.5 一起测**。

## 5. 对 S18（信仰）的专门警告

日志里说得很明白：**"实装了大量全新的教会互动内容，而每一个新互动都意味着每个 AI 角色在每个月都要多寻思一件事"** —— 这是他们本季度性能增长的最大来源。

⇒ 我们做信仰系统时必须带三条硬约束：

1. **交互按索引分发**，不做"每角色×每月×全交互"的笛卡尔积；
2. 信仰相关判定（正统/异端/传教/圣战）按**宗派→信仰**两级索引，不遍历所有 faith；
3. 每个新增交互必须在 M0.5 长跑里看到"日耗时增量"，**看不到增量的交互不许进主干**。

---

## 6. 与我们现有性能底座的关系

我们已有 `SimulationBudgetGovernor`（Min 4ms / Max 12ms / Target 16.7ms）+ `TickBudgeted` 延期队列 + `SimulationDirtySet` + `Parallel.For`——**骨架比 CK3 日志里描述的更接近目标**。缺的是：

- **两段式 tick**（Compute/Apply 分离）——没有；
- **每函数插桩**（调用次数）——没有；
- **长跑基准**（100 年日耗时曲线）——没有（M0.5 要补）。
