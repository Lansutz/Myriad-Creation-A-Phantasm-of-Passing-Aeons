## 1. 耦合矩阵：改 A 必须同步 B

> 判据不是"代码引用"，而是**机制上必须一致**。左列是"你动的东西"，右列是"同一提交里必须一起看的地方"。

| 改这个 | 必须同步 | 为什么（机制理由） |
|---|---|---|
| **教义/信条**（tenet/creed/dogma） | 宗派 `divergence`／正统 `orthodoxy`／婚姻资格／继承模式／司法处分／什一税／教育 | 教义是这些判定的**唯一来源**；改教义不改下游 = 规则与显示不一致 |
| **宗派状态**（mainstream/heterodox） | 合法性来源、臣民忠诚、继承权、异端迫害事件、编年史 | 判异端即是政治行为，不只是宗教标签 |
| **法律**（新增/废除/宪法化） | 税基与乘子、征募、司法、特许权撤销、合规度、编年史 | 法律效果必须落在**已有结算点**上，否则是纸面法 |
| **特许权** | 豁免/垄断的经济结算、司法管辖权、组织（修会/商会）存续、战争法理 | 特许权是"法律的例外"，两边都要认 |
| **头衔/官职** | 立法主体（proposalAuthority）、任命链、税收代征、军队指挥、继承 | 官职是"职权"的载体，职权决定谁能下什么令 |
| **关系层** | 附庸/朝贡义务 → 征税与征募；联姻 → 同盟；主保 → 庇护 | 关系是**权利义务**的容器，不是 UI 列表 |
| **社会四维**（阶级/阶层/身份/职业） | 需求四轴、法律人格效力、兵源、税负、职业产能 | 身份决定"适用哪套法"，职业决定"产出什么" |
| **人口/信仰构成** | 传教效果、异端比例、税收、兵源、城市合法性 | 人口是几乎所有结算的分母 |
| **革新** | 法律门槛、建筑解锁、单位解锁、教义宪法化 | 革新是"能不能做"的门 |
| **存档** | 上述**每一条新增字段** | 不入档 = 读档后历史断裂（我们已丢 20+ 字段） |
| **命名/归属**（本次新增） | 人物好感、编年史、聚落归属、工程结算 | 见 §4 |

### 1.1 同步规则（写进 DoD 的门禁）

任何"新增一个字段/状态"必须过**六问**，缺一项不算完成：

1. **谁写**（唯一写入口）？ 2. **谁读**（至少一个下游）？ 3. **入档**（DTO + 迁移 + 默认值）？ 4. **读模型/UI** 是否可见？ 5. **AI 是否使用**（否则玩家优势）？ 6. **是否留痕**（编年史/事件）？

> 我们已踩过的坑全能被这六问拦住：`stability` 三套夹取（多写）、`legalNormStage` 无写（无写）、`fundamentalizedLawIds` 无读（无读）、头衔不入档（不入档）、`isSecretBeliever` 无 UI（不可见）。

## 2. 教理（doctrine）详细施工 —— 用户点名的缺口

### 2.1 现状（事实）

- `Doctrines.json` **46 条平铺**；`DoctrineDef` / `DoctrineOptionDef` 无分组、无参数、无档位关系。
- 教义**不驱动任何判定**：婚姻、继承、性别、司法、税、教育六处都没有读它。
- `FAITH_DOCTRINE_CLASSIFICATION.md` 已把 CK3 的 49 组按"类型 × 领域"重排（126 档位，仅 44% 是规则），**但没落成我们自己的 schema**。

### 2.2 要建的东西（五件，按依赖排）

| # | 内容 | 产出 | 依赖 |
|---|---|---|---|
| 1 | **分组 schema** | `DoctrineGroup { id, field(神观/婚姻/性别/教职/政教/礼仪/司法/经济/教育/宗教间), options[] }`；`DoctrineOption { id, level, parameters{key:value}, effects[] }` | 无 |
| 2 | **教理层级** | `tenet`（原则，带 `authority ∈ {tenet, dogma}`）／`creed`（宣认，唯一）／`orthodoxy`（{包含, 排除}）／`canon`（文本清单，不装法规） | 1 |
| 3 | **内容重排** | 46 条按 §1 的十域挂组；缺口组补内容（婚姻资格、继承约束、性别角色、什一税、教育） | 1、2 |
| 4 | **判定** | `divergence = w1(1−tenetOverlap) + w2(liturgyDiff) + w3(preceptDiff)`（权重入内容表）；异端触发条件（正统边界 + 统治者立场 + 人数占比） | 3 |
| 5 | **接线六处** | 婚姻（谁可与谁婚）、继承（私生/异端继承权）、性别（任职/继承资格）、司法（处分种类）、经济（什一税/教会财产）、教育（谁识字/谁解释经典） | 3、4 |

### 2.3 验收（可断言）

1. 改一条 tenet → `divergence` 数值变化可复现，且宗派 `status` 按阈值迁移；
2. 两条宗派的 tenet 集合差 → 分歧度可算、可解释（不是手填）；
3. 教义改动后，**下游至少一处**行为改变（婚姻/继承/税/司法任一），并有测试。

### 2.4 我的判断（与用户口径的差异）

- 用户说"教义那一部分没详细计划"——**成立**，上面是补的施工。
- 但我不建议照搬 CK3 的 126 档位：其中过半是"身份标记/礼仪实践/关系/状态"，不是规则。**先做十域归组 + 每域 2–4 档**，够用且可维护；126 档是内容量，不是设计。

## 3. 命名：事件化（接受用户的方案，但要加约束）

用户方案："工程完成之后接一个命名事件，以谁为名；人还在世的话加好感度。"

**接受**，并补三条约束：

```
Construction/Engineering Plan 完成
   → NamingRequested(planId, settlementId, blockKind, candidates[])
       候选优先级：① Plan 发起者 ② 在位统治者 ③ 出资/庇护者
   → NamingService 决定（可能失败：人物已死/失势/被除名）
   → 写 block.builderCharacterId + displayName（= 该人物本名）
   → 若该人物在世：关系层 +opinion（对聚落统治者/对其家族） + 少量威望
   → 编年史：「某年，某人筑某某」；若被后世改名，记「后改称某」
```

| 约束 | 理由 |
|---|---|
| **好感走关系层**（`EntityRelation`），不新增字段 | 好感已经在 S17 有容器；新增字段=第七套关系 |
| **好感有上限与衰减** | 否则反复建墙刷好感；建议按人物一生累计上限，且与工程规模成正比 |
| **命名可失败** | 人死了、被放逐、工程由多方出资——"以谁为名"是政治结果，不是必然 |
| **可被后世改名** | 真实历史常见（政权更替后改称），也是编年史的好素材 |
| **不接文化命名表**（已定 D31） | 名字来自人物本名 |

## 4. 工作包（WP）与顺序

| WP | 内容 | 同步涉及系统 |
|---|---|---|
| **WP1 建造闭环** | Construction 补创建者（AI/玩家）→ 完成回调 → 命名事件 → 好感/编年史 | S15、S2、S4、S17、S13、S12 |
| **WP2 教理 schema + 重排** | §2 的 1–3 | S18、Content、M9 |
| **WP3 教理接线** | §2 的 4–5（六处下游） | S18、S6、S7、S4、S16 |
| **WP4 信息传播** | 谁知道什么（人物/地方/事件）；命令延迟 | S3、S15、S18、S17、M0.5 性能 |
| **WP5 Intrigue** | Scheme（含保密/暴露） | S15、S17、S6、S4 |
| **WP6 存档对齐 CK3** | 扁平表收尾 + 定义键串化 + 深度 | S13、全部 |

**顺序理由**：WP1 打通"建造-命名-归属"（收益立现、涉及面可控）；WP2/WP3 是用户点名的缺口；WP4 是 WP5 的前置；WP6 贯穿。

- S15 的 `PlanType` 判决（D32）会把 `Military/Trade/Diplomacy/Migration` 删掉——**M7（战争外交）的实现不能再走 Plan**，要改走 `Warfare`/`DiplomacyManager`。这是**计划内部矛盾**，必须同步改 M7 的施工口径。
