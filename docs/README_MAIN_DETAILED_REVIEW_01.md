# main/README 逐段复核记录 01

本文件用于记录对 main 分支 README 的逐段阅读结果。后续审计不能把 README 整体视作“当前设计”，必须按章节和状态判断。

## 本次已核对的高价值设计信息

### 世界与地理
README 明确把地理视为历史模拟底层条件，并描述：
- 多层高度图、侵蚀、大气环流；
- 水文：河流、流域、三角洲；
- 省份包含多个子地块；
- 地理与物产、革新、军事、人口、贸易联动。

注意：这些是高层设计说明，不等于当前每项算法均已实现。

### 革新
README 对革新的描述非常重要：
- 革新不是线性科技树；
- 物产是革新前置；
- 实践驱动；
- 品质影响实践贡献；
- 个人角色推动具体革新；
- 社会总体实践积累 + 个人突破；
- 数据驱动 JSON；
- 技术/思维/制度/传统 × 子类；
- 与经济、社会、政治、军事、文化联动。

其中“个人化革新”直接解释了为什么 PlanSystem 不应被误读成国家级万能计划系统：革新设计本身强调角色作为具体行动者。

### 聚居点
README 明确：
- 聚居点是文明的物理载体；
- Anchor 是空间定位实体，而非地块附属属性；
- 聚居点可跨多个地块；
- 关口堡可控制通道；
- 游牧营地可以迁徙；
- Burg / Outpost / Camp 三分类；
- 三者存在演化；
- 高等级城市有区划。

这里需要特别注意：这是项目设计意图，不代表当前 BurgData 已正确实现该模型。

### 聚居点毁灭
README 设计了完整连锁：
聚居点被破坏 → 人口流失/流民 → 周边地块无主 → 秩序下降 → 盗匪/蛮族滋生 → 战略/文化/政治后果。
这说明“Settlement destruction”不能简单等价为删除一个 Settlement 对象，也支持此前对 Settlement / Distribution / MapCell 分离的判断。

### MapActor / 自主单位
README 明确 MapActor：
- 不一定隶属于政权；
- 商队、流民、蛮族、盗匪、雇佣兵等；
- 前国家形态人群可以存在；
- 满足条件可转化为正式政权；
- 不同类型有不同 AI 思考周期；
- 与弃地、聚落毁灭形成生态循环。

这是已有代码与高层设计同时存在的领域。当前升级后的“Map Unit”边界应建立在这个基础上，而不是把 MapActor 当作简单 Army 替代。

### 角色系统
README 后半部分包含大量角色、关系、健康、信仰、家族、继承等设计。这些不能因为当前重构重点在 Map/Settlement 就忽略。尤其：
- 角色是多个系统的连接节点；
- 个人革新是角色行为；
- 角色关系有政治、家族、外交等维度；
- 健康/身体部位是未来逐步深化的系统。

后续如果审计 Plan / Activity / CharacterResearch，必须回到这些设计检查边界。

### 技术架构
README 给出了模块高层结构：
Core → World → Simulation → Rendering / Infrastructure / UI / Editor。
但这是模块设计说明，不应直接当成当前每个 asmdef 的精确依赖事实；实际依赖仍以代码审计为准。

### 开发路线
README 明确区分：
当前阶段：
- UI 基础控件材质；
- 架构重构与模块化；
- 革新与实践驱动；
- 聚落与建筑重构；
- 行国/城国双轨政权；
- 社会分层与阶层需求。

后续计划：
- 三军编制完整实现；
- 文化七大板块；
- 宗教双维度谱系；
- 个人化信仰/革新完善；
- 事件丰富；
- AI 完善；
- 模组工具。

这些“后续计划”不能作为当前代码缺失项直接判错，也不能当成已实现系统。

## 本次新增审计规则

以后阅读 README 不再采用“整份 README 一次性总结”的方式，而采用：

**章节 → 具体设计声明 → 当前代码证据 → 用户后续修订 → 状态判定**

状态至少分：
1. 当前有效设计；
2. 已实现；
3. 部分实现；
4. 设计未实现；
5. 已被用户后续设计升级/替换；
6. 明确未来计划；
7. README 仅作背景说明。

下一轮继续从 README 的经济/社会/政治/战争/文化/宗教/角色部分逐段核对，并将真正会影响 2.0 Domain Model 的内容提取出来；不会因为 README 写过就强行恢复旧架构。
